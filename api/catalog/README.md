# DEMOS — catalogo ufficiale delle opinioni (codice)

Snapshot in sola lettura dalla tabella `public.opinioni_domande` Supabase DEMOS del **28 ottobre 2026**: 94 voci con `id`, `text`, `gradi_opinione`, `approfondimento`. Le sei parti `opinions-part-00.json` — `opinions-part-05.json` sono combinate da `api/services/opinionCatalog.js` come catalogo immutabile. Nessuna risposta utente è inclusa.

- **ID stabili:** le risposte personali sono tuttora nelle colonne con questi ID in `opinioni_risposte`; non rinominare o riciclare ID senza piano di migrazione e conservazione storica.
- **Pubblicazione:** modifica tramite PR con test ed esplicita release backend. Le vecchie app Android continuano a utilizzare l'API; quindi un nuovo AAB non è obbligatorio solo per modificare le domande.
- **Proposte:** `opinioni_proposte` rimane database dinamico per proposte e voti. Nessuna proposta entra automaticamente nel catalogo ufficiale o viene approvata dall'app. Il rilascio ufficiale avviene via PR.
- **Parità di cutover iniziale (UNA SOLA VOLTA):** prima del primo rilascio del catalogo da codice verificare i 94 ID/testi/ambiti/approfondimenti con `node api/scripts/checkOpinionCatalogParity.js`, credenziali DB di sola lettura e rollback pronto. **Dopo il cutover**, le future aggiunte/rimozioni avvengono solo nel codice: non confrontare più ogni release con la vecchia tabella congelata; verificare invariabilità degli ID storici, test e migrazioni delle colonne delle risposte.
- **Rollback:** la tabella `opinioni_domande` non viene cancellata né modificata. Prima del cutover serve la verifica di tutte le route, i contratti legacy Android e le dipendenze SQL; database delle risposte e consensi rimangono autorevoli.

## Preflight bloccante prima del merge
- Primo passaggio: con un utente Postgres **solo SELECT** e connesso alla produzione, eseguire `DATABASE_URL=<read-only> node api/scripts/checkOpinionCatalogParity.js`. Verifica ID, testi, livelli, approfondimenti **e tutte le colonne risposte di tipo TEXT**. Al primo cutover rifiuta colonne mancanti, errate o extra; non legge le risposte personali.
- Per release **successive** (catalogo interamente nel codice), usare `--schema-only`: verifica ogni colonna pubblicata e lascia intatte le colonne di risposte archiviate; non confronta il vecchio catalogo del database, ormai congelato.
- Se il controllo fallisce, **non pubblicare** e non modificare automaticamente lo schema o gli utenti. Correggere in una migrazione approvata e ripetere le verifiche. Il preflight legge metadati e testo delle domande, mai risposte o consensi.


## Topologia dei router e compatibilità con status A (30 ottobre 2026)
- Il percorso di lettura effettivamente esposto dall'app è `GET /api/opinioni-list?grado=N|R|CO|E`, tramite `api/app.js` → `api/routes/compatibility.js`. La revisione pubblica `GET /api/opinioni-catalog-revision` è sullo stesso router. **Entrambi derivano il catalogo dal codice** e non interrogano `opinioni_domande`. Il primo continua a leggere autorizzatamente gli account e le **sole colonne delle risposte personali** della categoria richiesta; il secondo non esegue query SQL.
- Il modulo `api/routes/opinioni/compatibility.js` contiene ancora un helper di compatibilità per un vecchio endpoint nested, ma **non è montato** da `api/routes/opinioni/index.js`. I suoi test isolati non costituiscono prova della route in esecuzione: verificare sempre il percorso realmente montato tramite `api/tests/opinionCatalogRouteTopology.contract.test.js`, i test Android e la suite PG17.
- L'endpoint effettivo restituisce esclusivamente `opinion.id` del catalogo ufficiale, rifiuta parametri `grado` mancanti/malformati prima della query personale e considera attivo sia lo stato canonico `A` sia il precedente `a`; gli altri stati rimangono non autorizzati. Le regressioni PostgreSQL 17 ne coprono l'accettazione e il rifiuto.
- Questo intervento non cambia ID, domande, risposte, colonne SQL o comportamento della cache della **PR #464**, gestita separatamente. Il test su PostgreSQL in CI è sintetico, non sostituisce il preflight di parità 94/94 sul database reale immediatamente prima del cutover, né il collaudo Android o l'autorizzazione al merge/deploy.


## Check-missing: ID pubblicati senza introspezione SQL (30 ottobre 2026)
- `api/services/opinioniCheckMissing.js` usava `information_schema.columns` a **ogni richiesta** agli endpoint `/api/opinioni/check-missing-all` e `/api/opinioni/check-missing/:grado`, come se l'elenco delle domande pubblicate fosse una proprietà dinamica dello schema SQL. Ora `getColonneOpinioniRisposte` conserva il nome per compatibilità, ma costruisce il set di **soli ID pubblicati** da `getAllOpinions()` in memoria: zero query SQL per identificare il catalogo.
- Per le risposte individuali resta la necessaria query parametrizzata a `opinioni_risposte`; questa PR **non cambia** il formato delle risposte, il comportamento delle cache della PR #464 né le autorizzazioni. In `check-missing-all` viene eliminata una query di metadati per chiamata; in `check-missing/:grado` analogamente una.
- La corrispondenza fra ID pubblicati e colonne fisiche di `opinioni_risposte` è un **requisito del preflight di cutover**, non una lettura da rieseguire in ogni schermata. Se manca una colonna, la verifica runtime delle risposte non si autocorregge: il cutover deve rimanere bloccato finché la parità dello schema non è stata dimostrata, senza migrazioni automatiche.
- `api/tests/opinionCheckMissingCodeCatalog.test.js` verifica catalogo senza SQL, query personale invariata, livello provinciale `C`, assenza di risposte e grado non valido. I test C sono stati estesi anche alle suite Android/API e PG17. **Nessuna prova di produzione o nuovo deploy**.
